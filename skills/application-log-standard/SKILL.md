# 应用服务日志规范

为内网应用编写或审查日志代码、日志配置和日志样例时，遵循本规范。先检查项目已有日志框架和配置文件，并优先通过现有日志配置文件或配置中心实现通用日志能力；只有配置无法表达的业务上下文、链路采集或特殊脱敏逻辑才增加代码。按最小必要改动落实要求，不要为了日志改造引入与项目无关的框架或改变业务行为。适用于 Java、Python、Node.js 等应用。

## 总体要求

- 日志应可读、可检索、可关联、可用于运维排查。优先复用项目已有日志门面、实现和配置方式，不要仅为遵循某个框架偏好替换已可用的日志实现。Java 项目优先使用 SLF4J 门面；若项目已使用 Spring Boot 默认 Logback，应沿用并通过 `logback-spring.xml`、`application.yml` 等配置实现通用日志功能。异步日志适用于高吞吐且可接受异步写入的场景；需要严格时序或确保记录的关键场景可采用同步日志。
- **先配置，后写代码。** 日志级别、输出格式、标准时间/级别/线程/类名等记录头、JSON 编码、控制台和文件 appender、路径、按时间/大小滚动、压缩、保留期限/容量、异步策略及 logger 级别，优先放在项目现有日志配置文件或配置中心中统一管理。配置语法支持时，也用配置完成字段映射、MDC 注入和日志路由。仅当配置无法取得业务语义或运行时上下文时，才在代码中补充 `logType`、业务码、操作结果、耗时、错误分类、trace/span 等动态字段；不要在业务代码里手工拼日志头、序列化通用 JSON、管理文件滚动，或重复实现日志框架已有功能。
- 保持日志门面、日志实现和配置相匹配：SLF4J 是门面，不等于必须新增一种日志后端。使用 Spring Boot 时先确认 starter 带入的实际实现与版本，再选择 Boot 原生配置能力；只有现有实现确实无法满足需求，且有明确运维/平台要求时，才考虑增加依赖或切换后端。
- 支持以下七类 `logType`，按项目实际启用；默认启用全部类型。上线红线至少要求存在 `business_log`、`service_request_log`、`database_log`、`redis_log`、`mq_log` 五类记录。其余类型为 `service_run_log`、`performance_log`。
- 日志记录体使用结构化 JSON，字段名稳定、类型一致；每条记录都包含正确的 `logType`。避免仅拼接难以解析的自由文本来代替结构化字段。
- 日志关联应贯穿请求和服务调用。尽可能透传链路 ID；请求/链路记录提供 `spanId`、`parentSpanId`，以便按链路和父子关系检索。
- 仅记录排查和审计所需的信息。不得输出明文身份证号、手机号、银行卡号、邮箱、密码或用户姓名；按需脱敏：身份证保留前三位和后四位，手机号保留前三位和后四位，银行卡保留前六位和后四位，邮箱用户名保留前两位，密码全部替换为 `*`，姓名仅保留姓氏。也应避免在 SQL 参数、Redis 值、消息体、异常文本及调试日志中泄露个人信息、凭证或密钥。

## 日志类型及字段

各类型优先记录以下字段；根据场景补充有助于排障的字段，不要填造未知值。时间使用统一格式 `yyyy-MM-dd HH:mm:ss.SSS`；耗时使用数值并以毫秒计。

| `logType` | 记录时机与字段要求 |
| --- | --- |
| `business_log` | 记录关键业务操作的成功、失败和业务异常。必需字段：`operationType`、`requestTime`、`responseTime`、`channel`、`businessCode`。按需记录 `userId`、`beforeStatus`、`afterStatus`、`errorType`、`errorLevel`、`errorInfo`；用户标识不得暴露敏感信息。 |
| `service_run_log` | 记录应用启动、停止、重启及其异常。记录 `eventType`、`serviceVersion`、`instanceId`、`startTime`、`endTime`；按需增加 `duration`、依赖状态、停止原因和异常信息。正常启动/停止用 INFO；运行中断、启动失败等系统异常用 ERROR。 |
| `service_request_log` | 记录接口、HTTP/RPC/Feign 等服务调用链路。必须包含 `spanId`、`parentSpanId`、`requestUrl`、`method`、`result`、数值型 `resultCode`、数值型 `httpStatus`、数值型 `responseTimeConsume`。调用记录还必须包含 `callType`、`sourceService`、`targetService`、`protocol`、`requestTime`、`responseTime`。按需增加请求/响应大小、熔断状态及异常信息。 |
| `database_log` | 记录 SQL 执行、连接和事务操作。必须包含 `operationType`、`database`、`datasource`、`sql`、数值型 `executionTime`、`requestTime`、`responseTime`。SQL 使用参数化模板，不记录敏感参数明文；按需增加影响行数、事务/连接信息和异常信息。 |
| `redis_log` | 记录关键 Redis 操作及异常。必须包含 `key`、数值型 `costTime`、`executionTime`。Key 或值可能含用户标识时需脱敏；按需增加值大小、操作类型和异常信息。 |
| `mq_log` | 记录消息发送、消费、重试、堆积和死信等。必须包含 `messageId`、`topic`、`operation`、`sendTime`、`messageError`；无错误时仍保留 `messageError` 字段，可使用空值或明确的无错误约定。按需增加消费时间、耗时、重试次数、队列和消费组信息。消息体只记录必要摘要。 |
| `performance_log` | 记录性能和资源指标。按需包含 `metricName`、`metricType`、`metricValue`、`metricUnit`、`timestamp`、`instanceId`，用于性能分析和容量规划。 |

异常场景记录非空的 `errorInfo`；需要堆栈辅助定位时记录 `errorStack`。异常信息不得带出密码、令牌、个人信息或完整敏感请求内容。

## 记录头、级别与频率

- 标准记录头按顺序包含：时间、服务名称、`IP:端口`、链路 ID、线程号、日志级别、操作类。时间格式为 `yyyy-MM-dd HH:mm:ss.SSS`，级别使用 `DEBUG`、`INFO`、`WARN` 或 `ERROR`。项目因统一 JSON 日志采集而采用 JSON 头时，保持字段含义齐全、稳定，并遵循项目/平台统一配置。
- `INFO`：关键业务节点、请求结果、启动/停止等正常状态。
- `WARN`：可恢复异常、重试、降级、业务校验失败或潜在风险；避免高频重复输出。
- `ERROR`：系统运行时异常、代码缺陷、组件故障、不可恢复服务中断等。用户操作错误、参数校验失败、权限不足等正常业务拒绝不得记为 `ERROR`。
- `DEBUG`：仅用于诊断细节，生产环境默认关闭；临时开启应限定模块和时长，并及时恢复，避免持续输出影响性能或泄露数据。
- 高频请求、数据库、Redis 和消息操作避免无差别重复记录；根据调用量和排障价值选择采样或关键节点记录。异常必须保留足够的错误上下文和链路关联信息。

## 文件与滚动

- 运行日志文件名：`${app}[-${module}].log`；模块名可选。归档日志文件名：`${app}[-${module}].${yyyymmdd}.${type}.log.gz`，其中 `type` 为七种 `logType` 之一。
- 日志目录使用 `/data/logs/${app}`；如平台有统一挂载目录或集中日志平台要求，遵循平台配置，不在代码中硬编码环境专属路径。
- 配置按大小和时间滚动：单文件建议 200–500 MB，每日零点滚动；归档压缩为 `.gz`，配置保留期限或存储上限，并在适用时同步到统一日志平台。
- 全局、模块级日志级别及格式优先纳入配置中心管理；如果项目已有等效的统一配置机制，应沿用该机制。日志级别调整应尽量支持动态生效，临时 DEBUG 配置应自动恢复。

## 配置优先的实施和审查流程

1. **先查配置与依赖。** 确认实际日志门面/后端、框架版本、现有日志 XML/YAML/properties、配置中心和部署挂载方式；尽量沿用项目已有模式。
2. **优先改日志配置。** 先在配置层完成格式、日志头、级别、输出、滚动压缩、保留和路由等通用要求；使用环境变量或配置中心管理环境差异，不在代码中硬编码路径与级别。
3. **再补必要代码。** 只在业务边界记录配置本身无法推断的事件与字段，例如关键操作结果、业务码、耗时、异常分类以及请求链路 ID。使用 SLF4J 参数化/结构化日志 API 或项目既有工具，不手工拼 JSON；确保异步执行时链路上下文可正确传递。
4. 选择准确的日志类型与级别，补齐必需字段；检查 SQL、消息、缓存内容、异常和调试输出中的敏感信息并落实脱敏。
5. 验证配置生效、文件命名/目录/滚动/压缩/保留和平台同步要求。用项目测试或日志样例检查正常与异常路径的 logType、字段、级别、链路关联和 JSON 有效性。报告无法由代码或配置确认的运行环境要求，不要推断其已满足。
